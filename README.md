# drill

Локальный тренажёр для практики написания Go руками — без ИИ, без
автодополнения, без подсказок редактора.

Работает только на твоей машине, только для тебя: без аутентификации,
без деплоя, слушает петлевой интерфейс. Один бинарь, один файл базы.

```sh
go build ./cmd/drill && ./drill
# http://127.0.0.1:8080
```

## Как это работает

1. **Сегодня** — список на сессию: просроченные повторы плюс одна новая задача.
2. Открываешь задачу — слева условие, справа пустой редактор. Таймер стартует
   сам, на сервере.
3. Пишешь решение, жмёшь «Запустить тесты» (Ctrl/Cmd + Enter). Сервер собирает
   временный модуль из твоего кода и скрытых тестов задачи, гоняет
   `go test ./... -race` и стримит вывод в браузер.
4. Первый зелёный прогон останавливает таймер, сохраняет попытку и планирует
   повтор через 1 / 3 / 7 / 21 день.
5. После зелёного открывается **разбор**: твой код рядом с эталоном, отдельно
   то, что сделал бы `gofmt`, и поле «что я сделал криво». Заметка уходит
   в **журнал расхождений** — это и есть персональная программа тренировок.

Эталонное решение закрыто на сервере: `GET /api/tasks/{id}/solution` отдаёт
403, пока в базе нет ни одного зелёного прогона. Тесты задачи не отдаются
по API никогда.

## Как меряется прогресс

Пишутся два числа:

- `duration_ms` — настенные часы от открытия задачи до зелёного прогона;
- `active_ms` — только то время, когда вкладка в фокусе и ты что-то печатал.

Графики строятся по `active_ms`. Настенные часы считают и поход за кофе,
а тогда «объективно вижу прогресс» превращается в лозунг.

Повторы не понижают ступень лестницы при медленном решении: расписание
остаётся предсказуемым, а регрессии видно на экране статистики
(«на 40% медленнее лучшего»).

## Задачи

Лежат на диске в `./tasks/<id>/`:

```
tasks/slices-01/
├── task.yaml     id, title, topic, difficulty (1-3), estimate_minutes, race
├── README.md     условие
├── starter/      что откроется в редакторе
├── tests/        скрытые тесты — в UI не попадают
└── solution/     эталон, открывается после первого зелёного
```

`id` в `task.yaml` обязан совпадать с именем директории: иначе переименование
папки тихо потеряло бы всю историю попыток.

Сервис сканирует `./tasks` на старте и раз в две секунды опрашивает дерево по
отпечатку (имена, размеры, mtime). Файлового вотчера нет намеренно: на
полусотне директорий это сотня `stat`, зато ноль зависимостей и никаких
плясок вокруг того, как редакторы сохраняют файлы. Кнопка «Перечитать
./tasks» на экране задач делает то же самое немедленно.

Директория исключена из сборки вложенным `tasks/go.mod`: `starter/`, `tests/`
и `solution/` — это три версии одного пакета, вместе они не компилируются.

Стартовый набор — 10 задач на 5–15 минут: слайсы, мапы, интерфейсы, ошибки
с wrapping, горутины с WaitGroup, select с таймаутом, отмена по context,
дженерик Filter, свой UnmarshalJSON, HTTP middleware.

Каждая задача проверяется тестом `internal/tasksuite`: эталон обязан быть
зелёным, заготовка — красной. Сломанную задачу ловит CI, а не сессия.

## Раннер

Самая нетривиальная часть.

- Каждый прогон — свежая временная директория: сгенерированный `go.mod`,
  твои файлы, затем файлы из `tests/`. Порядок важен: решение не может
  подменить тест. Имена файлов из редактора валидируются отдельно
  (`..`, абсолютные пути, `go.mod`, `*_test.go` отклоняются).
- Директория удаляется всегда — `defer` ставится до любой работы, паника
  раннера ловится и превращается в обычный красный прогон.
- Вердикт разбирается из `go test -json`, а не регулярками по выводу.
  Начиная с Go 1.24 через тот же поток приходят и ошибки сборки.
- `-count=1`: с общим кэшем сборки `go test` иначе отдаёт закэшированный
  результат, и второй прогон того же кода ничего не проверяет.
- **Два таймаута.** Внутренний уходит в `go test -timeout`: тогда при
  зависании Go сам печатает `panic: test timed out` с полным дампом горутин —
  ровно то, что нужно на задаче про подвисшую горутину. Внешний дедлайн
  больше и работает как предохранитель, когда завис сам `go`.
- **Убийство группы процессов.** `exec.CommandContext` убивает только `go`,
  а собранный `pkg.test` продолжает крутить бесконечный цикл. Поэтому
  `Setpgid`, `SIGKILL` на `-pgid` и `WaitDelay`: без последнего `Wait`
  висит на пайпах, которые держит утёкший внук.
- **GOCACHE постоянный и общий** (`~/.cache/drill/gocache`). Кэш во временной
  директории превратил бы каждый прогон в пересборку стандартной библиотеки
  с `-race`.
- Окружение песочницы минимально: `GOPROXY=off`, `GOTOOLCHAIN=local`,
  `GOWORK=off`. Прогон герметичен и не ходит в сеть.
- Версия языка в сгенерированном `go.mod` — та, которую установленный
  тулчейн реально умеет запускать с `GOTOOLCHAIN=local`. Объявить версию
  новее означало бы переключение тулчейна на каждом прогоне, а с
  `GOPROXY=off` оно просто падает.
- На старте выполняется самопроверка: тривиальный пакет собирается и
  запускается через тот же конвейер. Сломанная песочница выглядит как «у
  меня всё не компилируется», и одна секунда на старте экономит сессию.
  Отключается флагом `-skip-self-check`.

Прогон живёт дольше HTTP-запроса, который его создал. `POST /api/runs`
возвращает `run_id`, события читаются отдельным `GET .../events` (SSE):
`EventSource` умеет только GET, перезагрузка страницы не должна убивать
компиляцию, а переподключение с `Last-Event-ID` доигрывает пропущенное.

## Фронтенд

Один HTML, три ES-модуля, один CSS — всё вшито через `embed.FS`. Ни сборщика,
ни npm, ни фреймворка.

CodeMirror 6 подключается через **import map** с точно закреплёнными
версиями: так в странице ровно одна копия `@codemirror/state` (две — самый
частый способ сломать самосборный CodeMirror).

`basicSetup` не используется: он тянет автодополнение и линтер. Редактор
собирается вручную из нужных расширений, а `@codemirror/autocomplete` вообще
отсутствует в графе загрузки — выключать нечего. Форматирование при
сохранении тоже не делается: писать по `gofmt` руками — часть тренировки,
а расхождение показывается потом, на разборе.

Если CDN недоступен, редактор откатывается на обычный `textarea` с
корректной обработкой Tab. Без подсветки синтаксиса, но тренироваться
можно офлайн.

Графики — самодельный inline SVG. Тянуть библиотеку ради линии и
горизонтальных столбиков незачем, и так страница работает без сети.

## Хранилище

SQLite через `modernc.org/sqlite` — чистый Go, без cgo. SQL руками, миграции
встроены через `embed.FS` и применяются на старте, каждая в своей транзакции.

Одно соединение (`SetMaxOpenConns(1)`). Пользователь один, конкурентности
нет, зато `SQLITE_BUSY` становится структурно невозможен.

Диск — источник правды. Таблица `tasks` это зеркало: исчезнувшая с диска
задача помечается `deleted_at`, а не удаляется, иначе `rm -rf` в `./tasks`
стирал бы всю историю. Зеркало нужно, чтобы статистика по темам считалась
в SQL.

Инварианты в схеме, а не в комментариях: `STRICT`-таблицы, `CHECK` на
сложность, частичный уникальный индекс «не больше одной открытой попытки на
задачу», `ON DELETE CASCADE` на снапшоты кода.

Даты повторов хранятся как локальный календарный день. С UTC «сегодня»
переключалось бы в три часа ночи, и утренняя сессия показывала бы вчерашний
список.

## Конфигурация

Флаги, значения по умолчанию берутся из `DRILL_*`, флаг всегда важнее.

| флаг | по умолчанию | зачем |
|---|---|---|
| `-addr` | `127.0.0.1:8080` | только петля: сервис выполняет произвольный код по HTTP |
| `-tasks` | `./tasks` | директория с задачами |
| `-db` | `$XDG_DATA_HOME/drill/drill.db` | вне репозитория, чтобы `git clean` не снёс историю |
| `-cache` | `$XDG_CACHE_HOME/drill/gocache` | общий кэш сборки |
| `-run-timeout` | `30s` | уходит в `go test -timeout` |
| `-hard-timeout` | `90s` | внешний дедлайн, убивает группу процессов |
| `-max-parallel` | `NumCPU/2` | одновременных прогонов |
| `-scan-interval` | `2s` | как часто пересканируется `./tasks` |
| `-skip-self-check` | выкл. | пропустить стартовую проверку песочницы |
| `-log-level` | `info` | `debug`, `info`, `warn`, `error` |

## Разработка

```sh
go test ./...              # всё, включая прогоны настоящего go test
go test ./... -short       # без компиляции Go-кода, секунды
go vet ./...
```

Тесты на сам сервис — table-driven, на настоящем SQLite во временном файле и
на настоящем тулчейне. Замоканы только те места, где реальная зависимость
ничего не проверяет. Раннер тестируется на реальных сценариях: ошибка
компиляции, бесконечный цикл, подвисшая горутина, паника, гонка под `-race`,
отмена посреди прогона, очистка песочниц.

## Установка на сервер

Есть, но с оговоркой: сервис без аутентификации выполняет произвольный код,
поэтому юнит слушает только петлю, а доступ идёт SSH-туннелем. Подробности
и скрипт — в [`deploy/`](deploy/README.md).

```sh
./deploy/install.sh                              # на сервере, от root
ssh -N -L 8080:127.0.0.1:8080 root@<server>      # у себя
```

## Добавить свою задачу

```sh
mkdir -p tasks/mytopic-01/{starter,tests,solution}
```

Заполни `task.yaml` и `README.md`, положи заготовку в `starter/`, тесты в
`tests/`, эталон в `solution/`. Сервис подхватит директорию в течение двух
секунд. Сломанная задача не роняет сервис: она попадает в список ошибок на
экране задач.

Перед коммитом прогони `go test ./internal/tasksuite/` — он проверит, что
эталон зелёный, заготовка красная, а всё вместе отформатировано `gofmt`.
